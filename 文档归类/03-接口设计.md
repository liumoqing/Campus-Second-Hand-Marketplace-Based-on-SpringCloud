### 1.2 请求头

| Header | 必填 | 说明 |
|---|---|---|
| `Authorization` | 除白名单 | `Bearer {accessToken}` |
| `Content-Type` | POST/PUT | `application/json;charset=UTF-8` |
| `Idempotency-Key` | 下单/支付必填 | UUID，10 分钟内同 key 返回同一结果 |
| `X-Trace-Id` | 否 | 前端可传，网关覆盖 |
| `internal-token` | 内部调用 | 服务间 Feign 由拦截器注入，浏览器不得携带 |

### 1.3 统一响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "b7f3c2a91d4e4b0c8f6a5d3e2c1b0a9f",
  "timestamp": 1793000000000
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| code | int | `0` 成功；其余见 `01-总体开发文档` §6.2 |
| message | string | 面向用户的提示语，前端可直接 toast |
| data | any | 业务数据，可为 `null` |
| traceId | string | 排查问题用，前端错误上报时带上 |
| timestamp | long | 服务端毫秒时间戳 |

**HTTP 状态码策略**

| 场景 | HTTP | body.code |
|---|---|---|
| 业务成功 | 200 | 0 |
| 业务失败（参数/状态/余额） | 200 | 对应错误码 |
| 未登录 / token 失效 | 401 | 10002 |
| 无权限（非 ADMIN 访问 /admin） | 403 | 10003 |
| 限流 | 429 | 10007 |
| 服务不可用 / 熔断降级 | 200 | 10007 |
| 网关路由不存在 | 404 | 10004 |

> 统一"HTTP 200 + code"是因为前端只写一处判断；401/403/429 保留 HTTP 语义，便于拦截器与监控。


> **参数校验失败一律 `10001`**（缺字段、类型不对、长度/格式不符、两字段互斥被同时传），message 里必须写清是哪个字段错了；**业务状态不对才用段内错误码**（30001 商品不存在、40002 状态不允许…）。`10003` 只表示"登录了但没权限"，不要拿它当参数错误用。
### 1.3.1 Sentinel 限流与降级契约（v1.9.2）

**网关限流**

| 项 | 行为 |
|---|---|
| 作用路径 | 仅精确匹配 `GET /product/page` |
| 阈值 | 20 QPS，1 秒统计窗口，快速失败 |
| 超限响应 | HTTP 429，body 为 `code=10007` |

```json
{
  "code": 10007,
  "message": "请求过于频繁，请稍后再试",
  "data": { "resource": "/product/page", "reason": "FLOW_LIMIT" },
  "timestamp": 1793000000000
}
```

**订单域服务降级**

| 场景 | HTTP | code | message |
|---|---:|---:|---|
| 商品查询调用不可用/熔断 | 200 | 10007 | 商品服务暂时不可用，请稍后再试 |
| 支付退款调用不可用/熔断 | 200 | 10007 | 支付服务暂时不可用，请稍后再试 |

- 规则由 Nacos 动态加载：网关键 `mall.sentinel.gateway-flow-rules`，订单键 `mall.sentinel.order-degrade-rules`。
- 订单规则采用异常比例 `grade=1`：统计窗口 10 秒、最少 5 次、异常比例 50%、熔断 10 秒。
- 当前范围只覆盖上述网关入口和订单域关键 Feign 调用；尚未启用 `productId` 热点参数限流，也未做全服务统一 Feign fallback。

### 1.3.2 OAuth2 授权端点（v1.10.0）

`mall-auth` 现为标准 Spring Authorization Server，平台端点如下（不计入 110 个业务接口）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/.well-known/oauth-authorization-server` | OAuth2 元数据发现 |
| GET | `/oauth2/authorize` | 授权码 + PKCE 授权入口 |
| POST | `/oauth2/token` | 授权码/刷新令牌/客户端凭证换 token |
| GET | `/oauth2/jwks` | RSA 公钥 JWKS，资源服务器验签 |
| POST | `/oauth2/revoke` | 撤销 token |
| POST | `/oauth2/introspect` | token 自省 |

- 公开 Web 客户端：`mall-web`，PKCE 必填，回调 `http://127.0.0.1:5173/oauth2/callback`。
- 服务端演示客户端：`mall-client`，使用 `client_credentials`。
- Access token 为 RS256 JWT，claims 含 `sub`、`uid`、`role`、`tv`、`jti`、`type=access`。
- 为兼容现有前端，`POST /auth/login` 仍返回同一套 RSA access token + 原有 refresh token；标准 OAuth2 流程可作为独立客户端接入。
- 网关资源服务器、下游 `@PreAuthorize` 和 WebSocket 握手均使用同一 JWKS 验签。
### 1.4 分页

请求参数：

| 参数 | 类型 | 默认 | 约束 |
|---|---|---|---|
| pageNum | int | 1 | ≥ 1 |
| pageSize | int | 10 | 1~50 |

响应 `data`：

```json
{ "records": [], "total": 128, "pageNum": 1, "pageSize": 10, "pages": 13 }
```

游标分页（消息、通知）用 `lastId` + `size`，返回 `{records, hasMore, lastId}`。

### 1.5 数据类型约定

| 类型 | 传输 | 说明 |
|---|---|---|
| Long（ID） | **字符串** | 防 JS 精度丢失，如 `"id": "1849203847562930176"` |
| BigDecimal（金额） | 字符串 | 如 `"price": "199.00"`，前端用 `Number()` 转换展示 |
| 时间 | 字符串 | `yyyy-MM-dd HH:mm:ss`（GMT+8） |
| 枚举 | 字符串 | 大写常量，如 `"ON_SALE"`，中文由前端 `enums.ts` 映射 |
| 布尔 | boolean | |

### 1.6 路径与参数规范

- 资源用名词复数：`/user/addresses`。
- 状态流转用子资源 + POST：`/order/{orderNo}/ship`。
- 路径变量带正则约束：`{id:\\d+}`，避免与静态路径冲突（如 `/user/profile` 与 `/user/{id}`）。
- 查询参数：`keyword`、`status`、`sort`（`new|oldest|price_asc|price_desc|hot|nearby`）、`pageNum`、`pageSize`。
  - `new` 最新发布 / `oldest` 最早发布 / `price_asc` 价格升 / `price_desc` 价格降 / `hot` 热度 / `nearby` 同城（按当前登录用户 `city` 或传入 `city` 过滤）
- 排序字段不接受前端传列名，只接受枚举。

### 1.7 幂等

| 接口 | 幂等键 | 实现 |
|---|---|---|
| `POST /order/create` | `Idempotency-Key` | Redis `SETNX mall:idem:{key}`，10 分钟，重复请求回查已建订单 |
| `POST /payment/pay` | `Idempotency-Key` + `uk_order_no` | 同订单只有一张支付单，重复调用返回已成功结果 |
| `POST /product/{id}/comments` | 无（允许重复评论） | 前端按钮节流 + 网关 IP 限流 |
| `POST /message/conversation` | `(user_a, user_b, product)` | `uk_conv` 唯一键 + 冲突回查，重复调用返回同一 `conversationId`（`created=false`） |
| `POST /message/send`、WS `CHAT` | `clientMsgId` | 同一 `clientMsgId` 只落一条，重发返回原 `msgId`（断网重连不产生重复气泡） |
| `POST /inner/message/card` | `orderNo + cardType` | 同一订单同一事件只写一条卡片（MQ 重试不刷屏） |
| MQ 消费 | `msgId` | Redis `SETNX` 24h |
| 支付回调 | `payNo + tradeNo` | `t_payment` 状态机 + 唯一索引 |

### 1.8 枚举字典接口

各服务提供 `GET /{domain}/dict`，返回本域枚举 `{枚举名: [{code, label}]}`，前端启动时拉取并缓存到 Pinia。已提供：`/user/dict`、`/product/dict`、`/order/dict`、`/payment/dict`。

### 1.10 角色、游客可见范围与强制下线

**三角色 + 游客**（`t_user.role`，见 02 文档 §4.1）

| 身份 | 判定 | 能做什么 |
|---|---|---|
| 游客（GUEST） | 无 token 或 token 无效 | **只能**：拿验证码、注册、登录、刷新 token、上传注册头像、首页看**前 20 条**商品、看分类树。**不能**看商品详情（P2 直接 10002）、不能评论/收藏/下单/私聊 |
| 普通用户（USER） | `role=USER` | 发布/编辑/下架自己的商品、评论、收藏、下单、支付、评价、私聊、维护资料与地址 |
| 普通管理员（ADMIN） | `role=ADMIN` | USER 全部能力 + `/admin/**`：看全部用户/商品/订单、**封禁/解封用户**、**限制/恢复上架权限**、强制下架违规商品、建分类、退款仲裁 |
| 超级管理员（SUPER_ADMIN） | `role=SUPER_ADMIN` | ADMIN 全部能力 + **设置角色**（U17，只能在 `USER ↔ ADMIN` 之间改）。**全系统只有一个，由初始化 SQL 插入，注册与后台都不能创建** |

**游客的 20 条硬限制（P1）**

| 规则 | 实现 |
|---|---|
| 只允许第 1 页、最多 20 条 | 游客请求时**忽略**前端传的 `pageNum/pageSize`，服务端强制 `pageNum=1, pageSize=20` |
| 不能翻页 | 响应固定 `pages=1`、并带 `"guestLimited": true`；页式响应**没有** `hasMore` 字段，前端只看 `pages` 与 `guestLimited`，把"加载更多"换成"登录查看更多" |
| 允许搜索/分类/排序 | 参数照常生效，但结果集仍然只有 20 条（用户拍板：能筛选，不能翻页） |
| 点卡片不能进详情 | 前端守卫拦：游客点卡片 → `/login?redirect=/product/{id}`；**后端兜底**：`P2/P3/P12` 对游客返回 10002，防止直接改地址栏绕过 |

**封禁（`t_user.status=BANNED` + `ban_until`）**

| 环节 | 行为 |
|---|---|
| 登录 | 返回 **20003**，`message` 固定为「您因违反用户规则已被封禁，解封时间{yyyy-MM-dd HH:mm:ss}」，`data` 带 `{ "banUntil": "...", "reason": "..." }`；`ban_until <= now` 时先自动解封再放行 |
| 已登录在线 | 封禁接口会 `token_version+1` 并写 Redis `mall:user:banned:{id}`；网关每次校验发现封禁标记 → 所有请求返回 20003；同时 `mall-message` 对该用户的 WS 连接推 `KICKED` 帧（含 `banUntil/reason`）→ 前端立即弹窗并跳登录 |
| 解封 | `status=NORMAL`、清 `ban_until/ban_reason`、`token_version+1`（旧 token 全部作废）、删 Redis 封禁标记 |
| 永久封禁 | `ban_until = 9999-12-31 23:59:59`，弹窗时间显示为 `9999-12-31 23:59:59` |
| 自动解封 | 每小时定时任务扫到期记录；登录/网关再各兜一次判断 |

**上架权限限制（`t_user.can_publish=0` + `publish_ban_until`）**

被限制的用户依然能登录、浏览、下单、私聊，只是**不能发布商品**：

- `P4 POST /product`、`P9 PUT /product/{id}/publish`、`P8 重新上架` 返回 **30009**，`data: { "publishBanUntil": "2026-11-02 10:00:00" }`；前端优先在点"发布闲置"按钮时用 `/auth/me` 里的 `canPublish/publishBanUntil` 本地拦截并弹窗，不依赖报错。
- 弹窗文案固定：「您因违反用户规则暂时无法上架商品，解封时间{yyyy-MM-dd HH:mm:ss}」。
- 恢复上架权限：`canPublish=1`、清 `publishBanUntil`；同样支持永久（9999）。

**@RequireRole 注解与网关分工**

- 登录态（`USER/ADMIN/SUPER_ADMIN`）由**网关**统一校验 token + `token_version` + 封禁标记，并把 `X-User-Id`、`X-User-Role` 注入下游。
- 细粒度角色（`ADMIN`、`SUPER_ADMIN`）由各服务 Spring Security `@PreAuthorize` 做方法级校验，`@RequireRole` 作为兼容兜底；`/inner/**` 不经过网关，用 `internal-token` 校验来源。

### A1 GET /auth/captcha

响应：

```json
{ "code": 0, "message": "ok",
  "data": { "captchaKey": "a1b2c3d4", "imageBase64": "data:image/png;base64,iVBORw0..." } }
```

> 验证码 2 分钟过期，校验后立即删除（一次性）。

### A2 POST /auth/register

**注册字段就是这 5 个 + 验证码**（用户要求：头像、用户名、邮箱、密码、确认密码）：

| 参数 | 类型 | 必填 | 校验 |
|---|---|---|---|
| avatar | string | 是 | 先调 A8 拿到 URL；必须是本站 MinIO 域名，否则 20007 |
| username | string | 是 | 4~20 位，字母数字下划线；唯一，重复 20001 |
| email | string | 是 | 合法邮箱 ≤ 64 字符；全局唯一，重复 **20006** |
| password | string | 是 | 8~20 位，必须同时含字母和数字 |
| confirmPassword | string | 是 | 与 password 一致，否则 20005 |
| nickname | string | 否 | 不传时默认取 `username`（前端注册表单可省这个字段） |
| captchaKey | string | 是 | |
| captchaCode | string | 是 | 错误 20004 |

```json
{ "avatar": "http://127.0.0.1:9000/mall/avatar/202610/a1.png",
  "username": "carol", "email": "carol@example.com",
  "password": "abc12345", "confirmPassword": "abc12345",
  "captchaKey": "a1b2c3d4", "captchaCode": "8f3d" }
```

响应 `data`：`{ "userId": "1849..." }`。

> **角色规则**：注册请求体里就算传 `role` 也会被忽略，落库永远 `role='USER'`、`status='NORMAL'`、`can_publish=1`。**管理员不能被注册**，只能由超管在后台用 U17 从普通用户提升。
> 邮箱只做格式与唯一性校验，v1 不发验证邮件（留作扩展：01 文档 §13.9）。

### A3 POST /auth/login

请求（`account` 可以是**用户名**，也可以是**邮箱**，大小写不敏感）：

```json
{ "account": "alice", "password": "12345678", "captchaKey": "a1b2c3d4", "captchaCode": "8f3d" }
```

> 服务端处理顺序：`account` 含 `@` → 按 `email` 查；否则按 `username` 查。两者都查不到统一返回 20002（不暴露"该账号是否存在"）。

响应：

```json
{ "code": 0, "message": "ok",
  "data": {
    "accessToken": "eyJraWQiOiI...RS256...",
    "refreshToken": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "userInfo": {
      "id": "1849203847562930176",
      "username": "alice",
      "nickname": "爱丽丝",
      "avatar": "http://127.0.0.1:9000/mall/avatar/1849/x.png",
      "email": "alice@qingchuan.local",
      "province": "湖北省", "city": "武汉市", "district": "洪山区",
```

> （`tv = t_user.token_version`，封禁/改角色后旧 token 自动失效，见 §1.10）。

### A4 POST /auth/refresh

请求 `{ "refreshToken": "..." }`；响应同 A3（**refreshToken 一次性轮换**，旧的立即失效）。失效返回 10002，前端跳登录。

### A5 POST /auth/logout

无请求体。服务端把 accessToken 的 `jti` 写入黑名单，删除 refreshToken。响应 `data: null`。

### A6 GET /auth/me

返回 `userInfo` 结构（每次页面刷新时调，用于恢复登录态）。

请求 `{ "oldPassword": "...", "newPassword": "..." }`；错误 20005 原密码错误。

### A8 POST /auth/avatar（注册用头像上传，公开）

注册第一步：**未登录也要能传头像**，所以这个接口在白名单里。

`multipart/form-data`：`file`（jpg/png/webp，≤ 2MB）。

响应 `data`：`{ "url": "http://127.0.0.1:9000/mall/avatar/202610/a1b2c3.png" }`。

| 约束 | 值 |
|---|---|
| 允许类型 | `image/jpeg`、`image/png`、`image/webp` |
| 大小 | ≤ 2MB（商品图是 ≤ 5MB、最多 5 张，两者上限不同） |
| 限流 | 同一 IP 1 分钟 5 次（Redis 计数），超限 10007 |
| 落库位置 | 经 Feign 转存 `mall-product` 的 `/inner/product/upload`（MinIO 路径前缀 `mall/avatar/`），返回可直读 URL |
| 与 P11 的区别 | P11 需要登录、支持 `bizType=product/review/chat`、≤5MB；A8 只服务注册，匿名、单张 |

> 该接口不做人像内容审核（本项目无审核环节），只校验类型/大小/是否真实图片（`ImageIO.read` 能解码）。

### A9 POST /auth/reset-code（找回密码：发码，公开）

登录页"忘记密码"的入口。本项目**没有邮件服务器**，所以做成"开发模式回显验证码"：

请求 `{ "email": "alice@qingchuan.local" }`

响应 `data`：`{ "sent": true, "expireSeconds": 600, "devCode": "481920" }`

| 规则 | 值 |
|---|---|
| 邮箱不存在 | **不报错**（返回 `sent:true`，避免探测注册邮箱），但 Redis 不写码 |
| 验证码 | 6 位数字，Redis key `mall:auth:reset:{email}`，TTL **10 分钟** |
| 限流 | 同一邮箱 1 小时内最多 3 次（第二次起 `devCode` 仍返回，便于本地调试），同一 IP 1 小时 10 次 |
| `devCode` | 仅当 `mall.auth.reset-code-echo=true`（本机默认 `true`）时返回；生产置 `false`，改为真实 SMTP |
| 成功码 | 200 |

> 这是"能在课程环境里跑通"的最短路径：接真实邮件只需把 `devCode` 换成 JavaMail 发送，接口契约不变。

### A10 POST /auth/reset-password（找回密码：重置，公开）

请求：

```json
{ "email": "alice@qingchuan.local", "code": "481920", "newPassword": "Qingchuan@2026", "confirmPassword": "Qingchuan@2026" }
```

响应 `data`：`{ "success": true }`；前端提示"密码已重置，请重新登录"。

处理 5 步：
1. 校验 `newPassword` 8~20 位且含字母与数字；两次不一致 → `20005`。
2. 取 `mall:auth:reset:{email}`，不存在/不匹配 → `20004`（验证码错误或已过期）。
3. 邮箱查用户（`/inner/user/credential?account=`，查不到也走第 2 步失败分支，不泄露是否存在）→ 调 `U18 /inner/user/{id}/password` 更新 BCrypt 密文。
4. `token_version + 1`（所有旧 token 立即失效，含"忘记密码后别的设备还登着"的场景），删验证码。
5. 返回成功；错误码只用 `20004` / `20005` / `10001`。

#### 后台用户管理（U12 ~ U17）

**U12 GET /user/admin/page**（管理后台"用户列表"）

| 参数 | 类型 | 说明 |
|---|---|---|
| keyword | string | **一个输入框搜全部**：命中 `username` / `email` / `nickname` / `phone`（模糊，最长 50） |
| role | string | `USER` / `ADMIN` / `SUPER_ADMIN`，不传=全部 |
| status | string | `NORMAL` / `BANNED`，不传=全部 |
| canPublish | int | `0` 只查被限制上架的人 |
| pageNum / pageSize | int | 默认 10，最大 50 |

响应（每行都能直接支撑后台表格与操作按钮的禁用态）：

```json
{ "records": [{
    "id": "1849...", "username": "alice", "nickname": "爱丽丝", "avatar": "http://...",
    "email": "alice@qingchuan.local", "phone": "138****8888",
    "role": "USER", "status": "NORMAL",
    "banUntil": null, "banReason": null,
    "canPublish": true, "publishBanUntil": null,
    "creditScore": 100,
    "lastLoginTime": "2026-10-26 19:30:00", "createTime": "2026-09-01 10:00:00"
  }],
  "total": 128, "pageNum": 1, "pageSize": 10, "pages": 13 }
```

> `operations` 由前端按"我是不是超管 + 目标是不是超管 + 目标是不是我自己"推导，后端不返回按钮权限，**但每个写接口都会再校验一次**。
> 列表里**不返回商品计数**（`onSaleCount/soldCount`）：一页 10~50 行去商品库逐个统计会变成 N+1，要看商品数请进 U13 详情页（那里再调 `P34 /inner/product/statistics/{sellerId}` 一次拿全）。
> `canPublish` 在响应里是 **boolean**（`true` 可上架），而 U12 的查询参数 `canPublish` 是 **`0/1` 的 int**（贴合前端下拉框的值）；两者语义一致，只是入参与出参的类型不同，别在联调时对不上。

**U13 GET /user/admin/{id}**：U1 结构 + `onSaleCount/soldCount/boughtCount/avgRating/banUntil/banReason/publishBanUntil`（商品计数来自 `P34`，订单统计来自 `/inner/order/statistics/{userId}`）。
> **不返回 `recentBans[]`**：`t_user` 只有当前封禁态（`ban_until/ban_reason`），没有封禁流水表；v1 展示"当前是否被封、到什么时候"即可，多次封禁的历史留给 01 §13.9 规划的操作审计表。

**U14 PUT /user/admin/{id}/ban**（封禁，ADMIN）

```json
{ "banUntil": "2026-11-02 10:00:00", "reason": "发布违规商品" }
```

| 参数 | 必填 | 说明 |
|---|---|---|
| banUntil | 二选一 | `yyyy-MM-dd HH:mm:ss`，必须 **晚于当前时间**；定时解封 |
| permanent | 二选一 | `true` = 永久封禁，服务端写 `9999-12-31 23:59:59`（此时 `banUntil` 可省略） |
| reason | 否 | ≤ 200 字，进弹窗与后台列表 |

处理步骤：校验目标存在且不是 `SUPER_ADMIN`（**20008**）、不是自己（**20009**）→ 更新 `status='BANNED'`、`ban_until`、`ban_reason`、`token_version+1` → 写 Redis `mall:user:banned:{id}`（value 为 `{banUntil,reason}`，TTL=封禁剩余时长；永久则 TTL=7 天并靠 DB 兜底）→ 删 `mall:user:tv:{id}` 缓存 → 发 MQ/WS，`mall-message` 对该用户在线连接推 `KICKED` → 响应 `data: { "banUntil": "2026-11-02 10:00:00" }`。

> 立刻生效：该用户已签发的 accessToken 因 `tv` 不匹配全部失效；网关看到封禁标记直接返回 20003，前端弹「您因违反用户规则已被封禁，解封时间…」并跳登录。

**U15 PUT /user/admin/{id}/unban**（解封，ADMIN）

无请求体。`status='NORMAL'`、清 `ban_until/ban_reason`、`token_version+1`、删 Redis 封禁标记与 tv 缓存。响应 `data: null`。已封禁用户需重新登录（旧 token 已作废，避免"解封即恢复旧会话"的安全问题）。

**U16 PUT /user/admin/{id}/publish-permission**（上架权限，ADMIN）

```json
{ "canPublish": false, "publishBanUntil": "2026-11-02 10:00:00", "permanent": false }
```

- `canPublish=false`：`can_publish=0` + `publish_ban_until`（`permanent=true` 写 9999-12-31 23:59:59），响应 `data: { "publishBanUntil": "..." }`。
- `canPublish=true`：恢复，清 `publish_ban_until`。
- 不影响登录与已上架商品，只拦住"发布/草稿发布/重新上架"三个动作（返回 **30009**，`data.publishBanUntil` 给弹窗用）。
- 同样禁止操作超管（20008）与自己（20009）。

**U17 PUT /user/admin/{id}/role**（设置角色，**仅 SUPER_ADMIN**）

```json
{ "role": "ADMIN" }
```

| 规则 | 错误码 |
|---|---|
| 只有 `SUPER_ADMIN` 可调用（ADMIN 调用 → 403 + 10003） | 10003 |
| `role` 只能是 `USER` 或 `ADMIN`，**传 `SUPER_ADMIN` 直接拒绝** | 20008 |
| 目标本身是 `SUPER_ADMIN`（包括自己） | 20008 |
| 目标就是自己 | 20009 |

成功后 `token_version+1`（让被改角色的人重新登录，拿到新 `role` 的 token）+ 删 tv 缓存 + 发站内通知（`type=SYSTEM`，文案"你的账号权限已变更为…"）。响应 `data: { "role": "ADMIN" }`。

### P1 GET /product/page

| 参数 | 类型 | 说明 |
|---|---|---|
| keyword | string | 标题/描述模糊匹配（最长 50） |
| categoryId | long | 分类（含子分类） |
| priceMin / priceMax | decimal | 价格区间 |
| city | string | 同城筛选（不传则不限；`sort=nearby` 时可省略，取当前登录用户城市） |
| conditionLevel | int | 成色下限 |
| sort | string | `new`（默认，最新发布）/`oldest`（最早发布）/`price_asc`/`price_desc`/`hot`/`nearby`（同城） |
| pageNum / pageSize | int | |

响应：

```json
{ "code": 0, "data": {
  "records": [{
    "id": "1849...", "title": "九成新 iPad Air 5", "price": "2600.00",
    "originalPrice": "4399.00", "coverUrl": "http://...",
    "province": "湖北省", "city": "武汉市", "district": "洪山区",
    "conditionLevel": 9, "freightMode": "DISTANCE",
    "sellerId": "1849...", "sellerNickname": "爱丽丝", "sellerAvatar": "http://...",
    "favoriteCount": 12, "commentCount": 3, "viewCount": 103,
    "createTime": "2026-10-20 09:12:00"
  }],
  "total": 128, "pageNum": 1, "pageSize": 20, "pages": 7, "guestLimited": false } }
```

> 只返回 `ON_SALE`（`DRAFT` / `OFF_SHELF` / `SOLD` 一律不出现在首页）。
> `categoryId` 语义：传一级分类时查询该一级及其全部启用子分类下的商品；传二级分类时只查询该二级分类下的商品。
> `sort=new` → `create_time DESC`，`oldest` → `create_time ASC`，`hot` → `view_count + favorite_count*3 DESC`，`nearby` → `WHERE city = :myCity` 后再按 `create_time DESC`。
> 首页一行 5 张卡片，前端 `pageSize` 建议传 20（4 行）。
>
> **游客（无 token）访问本接口时**：服务端忽略传入的 `pageNum/pageSize`，固定 `pageNum=1,pageSize=20`，响应 `guestLimited=true`、`pages=1`、`total` 为命中总数（可能 >20，但只给这一页）。搜索、分类、排序参数照常生效，但结果永远只有最多 20 条，前端不再请求第 2 页。**页式响应永远不带 `hasMore`**（那是游标分页 M3/通知的字段），前端判断"还能不能翻页"只看 `pages > pageNum`。
> 游客点任意卡片不能进详情（P2 返回 10002），前端守卫负责跳 `/login?redirect=/product/{id}`。
> 本接口由 Sentinel 精确限流：超过 20 QPS 返回 HTTP 429 + 10007，其他业务接口不受影响。

> **本接口要求登录**：游客调用直接 10002（HTTP 401），前端守卫在点击卡片时就把人引到登录页，不依赖这次报错。

### P4 POST /product

```json
{ "title": "九成新 iPad Air 5", "description": "…", "categoryId": 102,
  "price": "2600.00", "originalPrice": "4399.00", "conditionLevel": 9,
  "province": "湖北省", "city": "武汉市", "district": "洪山区",
  "freightMode": "DISTANCE",
  "coverUrl": "http://...", "images": ["http://...", "..."],
  "status": "ON_SALE" }
```

响应 `{ "productId": "1849...", "status": "ON_SALE" }`。

| 校验 | 规则 |
|---|---|
| 图片 | **1~5 张**，`coverUrl` 取 `images[0]`；URL 必须属于本站 MinIO 域名（防外链注入） |
| 价格 | `price > 0` 且 ≤ 999999.99；`originalPrice` 选填，传了必须 ≥ `price` |
| 标题 | 4~60 字 |
| 描述 | 选填，≤ 2000 字 |
| 分类 | `categoryId` 必填，且必须是启用状态的二级分类 |
| 地区 | `province/city/district` 必填，来自前端 Cascader |
| 成色 | `conditionLevel` 选填，范围 1~10；`10` 表示「全新」，`9~1` 表示「N 成新」，默认 9 |
| freightMode | `FREE_SHIPPING` / `DISTANCE` / `SELF_PICKUP`，必填 |
| status | 不传默认 `ON_SALE`；传 `DRAFT` 即存草稿（**只校验标题 4~60 字**，图片/分类/价格/地区允许后补，发布时由 P9 做完整校验） |

> **上架权限校验（先于业务校验）**：`t_user.can_publish=0` 且 `publish_ban_until > now` → 直接返回 **30009**，`data: { "publishBanUntil": "2026-11-02 10:00:00" }`，前端弹「您因违反用户规则暂时无法上架商品，解封时间…」。
> 若 `publish_ban_until <= now`，服务端先自动恢复 `can_publish=1` 再继续，用户无感。
> 该限制同样作用于 **P8 重新上架** 与 **P9 草稿发布**，错误码与 `data` 结构一致。
> 另外：`P8` 重新上架还需要商品属于本人且当前是 `OFF_SHELF`（否则 30005 / 30002）。

### P9 PUT /product/{id}/publish（草稿发布）

无请求体。草稿 → `ON_SALE`，**此时才做完整校验**（图片、价格、地区、运费方式齐全），缺项返回 30004 并带上缺失字段名，前端把这些字段标红。响应 `data: null`。

### P10 GET /product/my/page

参数：`status`（`DRAFT` 草稿箱 / `ON_SALE` 在售 / `SOLD` 已售 / `OFF_SHELF` 已下架，空=全部）、`pageNum`、`pageSize`。返回结构与 P1 一致，额外带 `status` 与 `offShelfReason`（本人的商品所以直接给，下架/被强制下架时要有文案，前端"已下架"角标 hover 显示）。 "我的"页 4 列商品墙与"我的交易→我发布的"共用此接口。

### P11 POST /product/upload

`multipart/form-data`：`file`（≤5MB）、`bizType`（`product|avatar|review|chat`）。响应 `{ "url": "http://127.0.0.1:9000/mall/product/202610/xxx.png" }`。

### P12 GET /product/{id}/comments（商品评论区）

参数：`pageNum`、`pageSize`（默认 10）、`sort`（`new` 最新 / `hot` 最多回复）。返回一级评论 + 每条附带的回复：

```json
{ "records": [{
    "id": "7701", "content": "这个还在吗？能不能小刀", "images": [],
    "user": { "id": "1850...", "nickname": "小鲍", "avatar": "http://..." },
    "replyCount": 1,
    "replies": [{ "id": "7702", "parentId": "7701", "content": "在的，诚心价 2500",
                  "user": { "id": "1849...", "nickname": "爱丽丝", "avatar": "http://..." },
                  "createTime": "2026-10-24 10:02:00" }],
    "createTime": "2026-10-24 09:58:00"
  }],
  "total": 3, "pageNum": 1, "pageSize": 10, "pages": 1 }
```

> `replyCount` 是**聚合出来的**（`SELECT parent_id, COUNT(*) FROM t_product_comment WHERE product_id=? AND parent_id<>0 AND status=1 AND deleted=0 GROUP BY parent_id`），表里没有这一列。
> `sort=hot` 按 `replyCount desc, create_time desc` 排（内存里排，评论页数据量小；数据量大再加冗余列）。
> 查询条件固定 `parent_id=0 AND status=1 AND deleted=0`：`status=0` 是管理员隐藏的违规内容，`deleted=1` 是本人删掉的，两者都不能出现。

### P13 POST /product/{id}/comments

```json
{ "content": "这个还在吗？", "images": ["http://..."], "parentId": "7701" }
```

`parentId` 不传 = 一级评论；传了 = 回复该评论（只能是同一商品下的一级评论）。响应 `{ "commentId": "7703" }`。
限制：`content` 1~500 字，`images` ≤ 3 张，同一用户对同一商品 1 分钟内最多 3 条（Redis 计数）。评论成功 `t_product.comment_count + 1`。

> 商品评论**不打分**、不影响卖家评分（评分只来自订单的双向互评 `t_review`）。卖家可回复自己的商品评论区任一条（等价 P13 带 `parentId`）。

### P14 DELETE /product/comments/{id}

删除自己的评论（ADMIN 可删任意）；二级回复随父评论一起逻辑删除。响应 `data: null`，`comment_count` 相应扣减。

### P21 POST /category/admin（管理员新建分类）

```json
{ "parentId": 0, "name": "数码电子", "icon": "http://...", "sort": 1 }
```

响应 `{ "categoryId": "8" }`。规则：
- `parentId=0` 为一级分类；**只允许两级**，`parentId` 必须为 0 或某个一级分类 id。
- `name` 同级唯一，由 `uk_parent_name(parent_id,name,deleted)` 兜底（不是"先查再插"）。

| 情况 | 错误码 |
|---|---|
| `parentId` 指向的分类不存在 | `30006` 分类不存在 |
| 在二级分类下再挂子级（超过两级） | `30008` 分类层级超限 |
| 同级已有同名分类 | `10001`（message 写"同级已存在同名分类"） |

### P22 PUT /category/admin/{id}

`{ "name": "…", "icon": "…", "sort": 2, "status": 0 }`（`status=0` 停用后：首页左栏不再展示、发布页不可选，已有商品不受影响）。响应 `data: null`。

### P23 DELETE /category/admin/{id}

仅当该分类（含子分类）下**没有商品**时可删，否则 30007 并返回商品数；删除为逻辑删除。响应 `data: null`。

### P25 PUT /product/admin/{id}/off-shelf（管理员强制下架）

`{ "reason": "描述含违规内容" }`。商品转 `OFF_SHELF`，清 Redis 缓存，调 M11 向卖家发站内通知：`type=SYSTEM`、`title=商品已被平台下架`、`bizType=PRODUCT`、`bizId=商品ID`，正文包含商品标题与下架原因；卖家 `P8` 可重新上架。响应 `data: null`。
ADMIN 无"通过/驳回"动作——平台不审核，只治理。

### O1 POST /order/create（核心接口）

Header：`Idempotency-Key: 3f2a...`（必填）

请求：

```json
{ "productId": "1849...", "addressId": "1849...", "remark": "周末下午自提" }
```

响应：

```json
{ "code": 0, "data": { "orderNo": "O20261026193500004213",
                       "totalAmount": "2600.00", "freight": "5.00",
                       "payAmount": "2605.00", "status": "UNPAID",
                       "sameCity": true } }
```

**校验顺序**

1. `Idempotency-Key` 命中 → 直接返回已建订单。
2. 商品存在且 `ON_SALE`（否则 30002）；`sellerId != 当前用户`（否则 40003）。
3. 地址属于本人（否则 10004）；`freightMode=SELF_PICKUP` 且跨城 → 40004。
4. **算运费**：`FREE_SHIPPING` → 0；`SELF_PICKUP` → 0；`DISTANCE` → 地址 `city == 商品 city` 即 5.00，否则 10.00。
5. 开 Seata 全局事务（2 个分支）→ `mall-product` 扣库存并置 `LOCKED` → `mall-order` 建单。
6. 提交后发 RocketMQ 延迟消息（30 min），用于超时取消。

**错误码**：30002、30003、40003、40004、10006（重复提交）、10007（商品服务熔断/降级）。

> 商品服务不可用时，订单接口返回 HTTP 200、`code=10007`，message 为「商品服务暂时不可用，请稍后再试」；不会把底层 Feign 异常堆栈暴露给前端。

> v1.1 起下单事务**不再涉及支付库**（没有钱包冻结）：Seata 的参与者是 `mall-product` 与 `mall-order` 两个库——跨库全局事务仍在，链路更短。

### O7 双向评价（重点）

**方向由调用者身份自动判定**，前端不用传 `direction`：

- 调用者是该订单的 **buyer** → `direction = BUYER_TO_SELLER`（评卖家，落 `t_order.buyer_reviewed`）
- 调用者是该订单的 **seller** → `direction = SELLER_TO_BUYER`（评买家，落 `t_order.seller_reviewed`）

规则：

1. 仅 `COMPLETED` 订单可评；同一方向只能评一次（`uk_order_direction` 兜底，重复返回 40005）。
2. `rating` 1~5 必填；`content` 选填 ≤ 500 字；`images` ≤ 3 张。
3. 评价提交后**不可修改**，可选 `anonymous` 隐藏昵称（头像仍显示）。
4. 双方都评完或 15 天到期后，`t_order` 标记结束（`finish_time` 已是收货时间，这里只做提醒，不阻塞）。
5. 评分展示：卖家/买家的 `avgRating` 一律只取"别人评我的"那一半，见 §5 的 O11 与 §3 的 U3。

### O12 退款 / 售后

同一个接口承担两种场景，**靠订单当前状态区分**，前端按钮文案不同（未收货叫"申请退款"、已完成叫"申请售后"）：

| 订单状态 | 语义 | 可申请窗口 |
|---|---|---|
| `UNSHIPPED` | 未发货退款 | 随时（发货前） |
| `UNRECEIVED` | 已发货未收货退款 | 收货前 |
| `COMPLETED` | **收货后售后** | 仅在 `finishTime` 起 **7 天内**，超期返回 `40008` |

请求 `POST /order/{orderNo}/refund`，请求体 `{ "reason": "有暗病", "amount": "2600.00" }` → 生成退款单，订单转 `REFUNDING`，返回 `{ "refundId": "...", "refundNo": "R2026...", "status": "APPLYING" }`。
- 申请时把订单当前状态快照进 `t_refund.before_status`，拒绝时按它回退（见下方 O13）。
- 同一订单**只能申请一次**（`t_refund.uk_order` 兜底）→ 重复申请返回 `40007`。
- `amount` 必须 ≤ `pay_amount`，否则 `50004`。
- 订单不在上述三态之一（如 `UNPAID`/`CANCELLED`）→ `40002`。
- 申请成功后向**卖家**发送站内通知（`type=REFUND`、`title=退款申请待处理`、`bizId=orderNo`、`bizType=ORDER`），同时发送 `REFUND_APPLIED` 订单卡片；消息服务失败只记日志，不回滚退款单。

O13 处理：`PUT /order/refund/{id}/handle`，请求体 `{ "agree": true|false, "remark": "…" }`。仅退款单对应的卖家或 ADMIN 可调用，其他登录用户返回 `10003`。
- **同意用布尔值并落最终态**：`agree=true → t_refund.status='REFUNDED'`、`agree=false → 'REJECTED'`；不是用 `action=AGREE|REJECT`。
- 同意则调 `Y4 /inner/payment/refund` 退款、订单转 `REFUNDED`、按 01 §8.9 决定商品是否回收（未发货退款 → 商品回 `ON_SALE`；已收货售后 → 商品保持 `SOLD`）。
- **拒绝则按 `t_refund.before_status` 回退**（申请时快照的订单状态）：申请前是 `UNSHIPPED` 就回 `UNSHIPPED`、是 `UNRECEIVED` 就回 `UNRECEIVED`、是 `COMPLETED` 就回 `COMPLETED`——**不要写死 `UNRECEIVED`**，否则"未发货退款被拒"会凭空变成"已发货待收货"。
- 订单当前状态不是 `REFUNDING`、或该退款单已被处理过 → **40002**；退款单不存在 → 10004。
- 处理完成后向**买家**发送退款结果站内通知：同意为「退款已同意」，拒绝为「退款申请已拒绝」；同意时另发 `REFUND_DONE` 订单卡片。
- 支付退款调用不可用/熔断时返回 code=10007，message 为「支付服务暂时不可用，请稍后再试」；退款单保持原状态，便于重试。
- 前端入口：卖家在 `/orders?tab=REFUND&role=sold` 查看「我卖出的」退款单并审批；系统通知中的「去处理退款」按钮直接携带这两个查询参数跳转。

### Y1 POST /payment/pay

```json

```

```json

```

处理流程（同步完成，前端拿到 `SUCCESS` 直接跳"我的订单"）：

1. 校验订单属于当前用户且 `status=UNPAID`（否则 50002）；调 `/inner/order/{orderNo}` 取应付金额。

5. 返回 `SUCCESS`。

### M2 GET /message/conversations（会话列表）

参数：`?pageNum=1&pageSize=20&keyword=`（`keyword` 可选，匹配对方昵称或会话关联的商品标题；不传即全部会话）。


一个接口承担两种"已读"，靠请求体区分：

```json
// ① 聊天：把某会话里 upTo 之前的对方消息标为已读，并清该会话未读
{ "conversationId": "9001", "lastMsgId": "88012" }

// ② 系统通知：标指定通知为已读；传空数组表示全部已读
{ "noticeIds": ["7001", "7002"] }
{ "noticeIds": [] }
```

- 两种字段**互斥**：都传返回 `10001`（参数校验失败）；`conversationId` 与 `noticeIds` 都不传也 `10001`。
- 通知语义下 `noticeIds` 明确传 `[]` 表示清空该用户全部通知未读，避免只清当前分页仍残留红点。
- 幂等：重复标记不报错，直接返回成功。
- 成功后服务端同步递减 `mall:msg:unread:{userId}` 的对应计数，前端以响应里的 `{ unreadTotal }` 覆盖本地值。

### M6 GET /message/notices（系统通知列表）

聊天页左侧列表第一项「系统通知」用：分页查 `t_notice`，按 `create_time desc`。

请求：`?pageNum=1&pageSize=20&type=&unreadOnly=false`（`type` 可选 `SYSTEM/ORDER/REFUND`）

响应：

```json
{ "records": [{
  "noticeId": "7001", "type": "ORDER", "title": "你的订单已发货",
  "content": "订单 202610261200001234 已由卖家发货，请注意查收",
  "bizId": "202610261200001234", "bizType": "ORDER", "isRead": false,
  "createTime": "2026-10-26 20:01:00" }],
  "total": 12, "pageNum": 1, "pageSize": 20, "pages": 1, "unreadCount": 3 }
```

- 进入页签后前端调 `M5 PUT /message/read`，请求体为 `{"noticeIds":[]}` 将全部通知标为已读；成功后重新拉取 `M10` 未读数并清红点。WS `NOTICE` 帧只触发服务端未读数刷新，不在本地盲目 `+1`。
- **跳转只看 `bizType`，不要猜 `bizId` 的格式**：`ORDER` → `/orders?orderNo={bizId}`；`PRODUCT` → `/product/{bizId}`；`USER` → `/admin/users?keyword={bizId}`（仅管理员可见）；`NONE`/空 → 不跳转，只展示文字。
- `unreadCount` 是该过滤条件下的未读数（不带 `type` 时即全部未读）；顶部红点用 `M10` 的 `total`，两者在"按 type 过滤"时会不同，前端不要互相覆盖。

### M12 POST /message/conversation（建/取会话，幂等）

详情页点"联系卖家"、订单页点"联系卖家"、卡片里的"回复"都先调它拿到 `conversationId`，再跳 `/chat?cid=xxx`。

请求：

```json
{ "peerId": "1850...", "productId": "1849...", "openWithProductCard": true }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `peerId` | 是 | 对方 userId；**等于自己返回 60002** |
| `productId` | 是 | 会话归属商品（`uk_conv` 的一部分）；订单卡片也用它定位会话 |
| `openWithProductCard` | 否 | 默认 `true`：首次建会话时自动发一条 `PRODUCT` 卡片作为开场，对方一眼知道你在问哪件商品；已存在的会话不重复发 |

响应：`{ "conversationId": "9001", "created": true }` —— `created=false` 表示会话本来就存在（幂等命中）。

服务端行为：

1. 校验 `peerId` 存在、未被封禁 → 被封禁直接返回 `60003`（建会话这一步就拦住，不留下"能建会话却发不出消息"的半吊子状态）；不能是自己（60002）。
2. `getOrCreateConversation(minId, maxId, productId)`；`uk_conv` 冲突即回查，返回 `created=false`。
3. `openWithProductCard && created` → 用 `/inner/product/{id}` 取标题封面价格，写一条 `PRODUCT` 卡片，推给对方。
4. **不重置未读数**；对方未读 +1。

常见错误：`60002` 不能和自己会话、`60003` 该用户已被封禁、`10004` 商品不存在、`10001` productId 缺失。

### M13 POST /inner/message/card（订单卡片，内部）

只有 `mall-order` 调，浏览器无法直接调（网关不路由 `/inner/**`）。

```json
{ "orderNo": "O20261026193500004213", "cardType": "ORDER_SHIPPED",
  "buyerId": "1850...", "sellerId": "1849...", "productId": "1849...",
  "productTitle": "九成新 iPad Air 5", "productCover": "http://.../a.jpg",
  "statusText": "卖家已发货", "actionText": "查看订单" }
```

服务端：按 `(buyerId, sellerId, productId)` 取/建会话 → 以 `fromId=事件发起方`（发货是卖家、下单是买家）写一条 `content_type=ORDER`、`card_type=cardType` 的消息，卡片 `content` 固定包含 `productTitle/productCover` → 推 WS 给对方 → 对方未读 +1；在线 0.5 秒内到达，离线落库等上线。

**卡片发送时机（一张表定死，order 服务照它发）**

| 业务事件 | `cardType` | 发件人 → 收件人 | `statusText` | 按钮 |
|---|---|---|---|---|
| 买家下单成功（订单落 `UNPAID`） | `ORDER_CREATED` | 买家 → 卖家 | 买家已下单，等待付款 | 查看订单 |
| 买家支付成功（订单转 `UNSHIPPED`） | `ORDER_PAID` | 买家 → 卖家 | 买家已付款，请尽快发货 | 去发货（卖家侧路由 `/orders?tab=unshipped`） |
| 卖家发货（订单转 `UNRECEIVED`） | `ORDER_SHIPPED` | 卖家 → 买家 | 卖家已发货，请注意查收 | 查看订单 |
| 买家确认收货（订单转 `COMPLETED`） | `ORDER_RECEIVED` | 买家 → 卖家 | 买家已确认收货 | 去评价 |
| 买家取消 / 超时关闭（`CANCELLED`） | `ORDER_CANCELLED` | 买家 → 卖家 | 订单已取消 | 查看订单 |
| 买家申请退款（`REFUNDING`） | `REFUND_APPLIED` | 买家 → 卖家 | 买家申请退款，请处理 | 处理退款 |
| 退款完成（`REFUNDED`） | `REFUND_DONE` | 卖家 → 买家 | 退款已完成 | 查看订单 |

> 卡片与站内通知（`t_notice`）**同时发**：卡片给"聊天窗口里看得到"的即时感，通知给"没进聊天页也不漏"的兜底。两者内容同源，避免只发一种时用户漏看。

### WebSocket 协议（M1）

**连接**：`ws://localhost:4399/ws/chat?token={accessToken}`；网关校验 token 后转发，注入 `X-User-Id`。握手失败返回 `10002` 并关闭。

**帧格式**

```json
{ "type": "CHAT", "clientMsgId": "c-20261026-1", "conversationId": "9001",
  "toId": "1850...", "productId": "1849...", "contentType": "TEXT",
  "cardType": null, "content": "还在吗？", "createTime": "2026-10-26 20:01:00" }
```

> **帧里的字段名和时间格式与 HTTP 接口完全一致，不要另立一套**：上行收件人叫 `toId`（不是 `toUserId`）；时间叫 `createTime` 且是 `yyyy-MM-dd HH:mm:ss` 字符串（不是毫秒 `ts`）；服务端回执 `type` 就叫 `ACK`（不是 `CHAT_ACK`）；所有 `Long` 主键在帧里同样是**字符串**（与全局 Jackson 配置一致，避免 JS 精度丢失）。

| type | 方向 | 服务端行为 |
|---|---|---|
| `CHAT` | C→S | 校验、落库、更新会话、推送给对方，回 `ACK`。`contentType` 允许 `TEXT` / `IMAGE`（`PRODUCT` / `ORDER` **只在服务端产生**，客户端传了直接拒，返回 60004） |
| `ACK` | S→C | `{ type:"ACK", clientMsgId, msgId, createTime }` |
| `READ` | C→S | `{ type:"READ", conversationId }`，清零未读并通知对方 |
| `CARD` | S→C | 服务端推送订单/商品卡片：`{ type:"CARD", msgId, conversationId, cardType, contentType:"ORDER", content:{...}, createTime }`（与 `CHAT` 同构，独立 type 只为让前端能加"新卡片"提示音） |
| `ONLINE` / `OFFLINE` | S→C | 对方在线状态：`{ type:"ONLINE", conversationId, peerId }` |
| `NOTICE` | S→C | 系统通知推送（订单事件、退款结果、商品被下架、账号治理） |
| `KICKED` | S→C | 强制下线：`{ reason:"BANNED" | "OTHER_LOGIN", banUntil?, message? }` |
| `PING` / `PONG` | 双向 | 30s 心跳，60s 无响应断开 |

**错误帧**：`{ "type": "ERROR", "code": 60002, "message": "不能给自己发消息" }`

**离线**：消息一律落库，上线后 `M3` 拉增量；未读数以 Redis Hash 为准，DB 兜底。

**发消息的校验顺序**（`CHAT` 与 `M4 /message/send` 共用，别写两套）：

1. 会话属于我（`conversationId` 里有我的 userId）→ 否则 60001。
2. `toId` ≠ 自己 → 否则 60002。
3. 我不是被封禁状态（网关已拦，这里再兜一次）→ 否则 20003。
4. `contentType` ∈ {TEXT, IMAGE} → 否则 60004。
5. TEXT 长度 ≤ 500、IMAGE 必须是本站上传的 URL → 否则 60005。
6. 同一用户 1 秒最多 3 条（Redis 令牌桶），超了返回 60006（前端提示"发太快了"）。

## 8 内部接口：mall-user

| 方法 | 路径 | 调用方 | 说明 |
|---|---|---|---|
| GET | `/inner/user/credential?account=` | auth | 取登录凭证：`account` 是用户名**或邮箱**，返回 `{userId,username,email,password,status,role,nickname,avatar,tokenVersion,banUntil,banReason,canPublish,publishBanUntil}` |
| POST | `/inner/user` | auth（注册） | 创建账号 `{username,email,password,nickname,avatar}` → `{userId}`；**角色固定写入 USER**，不接受 `role` 字段 |
| GET | `/inner/user/{id:\d+}` | product/order/message | 精简用户信息 `{id,nickname,avatar,city,creditScore,signature,lastLoginTime,createTime}` |
| POST | `/inner/user/batch` | product/order/message | 批量 `{ids:[]}` → `{id: {nickname,avatar,creditScore}}` |
| PUT | `/inner/user/{id:\d+}/credit` | order | 调整信用分 `{delta:-2}` |
| PUT | `/inner/user/{id:\d+}/password` | **auth（A10 找回密码 / A7 改密）** | 重置密码 `{password}`（已 BCrypt 的密文或明文由 auth 侧决定，**传密文**），同时 `token_version+1`；不校验旧密码（旧密码校验在 auth 侧完成） |

> `/inner/user/credential` 是登录的唯一数据来源：`mall-auth` 不建库，注册也经 `POST /inner/user` 落到用户库；邮箱唯一性在用户库用 `uk_email` 兜底，冲突时返回 20006 给 auth 再透传给前端。
> `tokenVersion` 供 auth 写进 JWT 的 `tv` claim；`banUntil/banReason` 供 20003 的弹窗文案；`canPublish/publishBanUntil` 供登录响应回给前端做按钮禁用。

示例（batch）：

```json
POST /inner/user/batch   { "ids": ["1849...", "1850..."] }
→ { "code": 0, "data": { "1849...": { "nickname": "爱丽丝", "avatar": "http://...", "creditScore": 100 } } }
```

| 方法 | 路径 | 调用方 | 说明 |
|---|---|---|---|
| GET | `/inner/payment/order/{orderNo}` | order | 查询该订单支付单 `{payNo,status,payAmount,refundAmount}` |
| POST | `/inner/payment/refund` | order | `{orderNo, amount}` 把支付单 `SUCCESS → REFUNDED` 并写 `refund_amount/refund_time`；**幂等**：`UPDATE ... WHERE status='SUCCESS'` 影响 0 行即视为已退，直接返回成功 |

## 12 前端调用示例

```ts
// src/utils/request.ts（节选）
const service = axios.create({ baseURL: import.meta.env.VITE_API_BASE, timeout: 10000 })

service.interceptors.request.use((cfg) => {
  const token = useUserStore().accessToken
  if (token) cfg.headers.Authorization = `Bearer ${token}`
  cfg.headers['X-Trace-Id'] = uuid()
  return cfg
})

service.interceptors.response.use(
  (res) => {
    const r = res.data as R<any>
    if (r.code === 0) return r.data
    if (r.code === 10002) return refreshAndRetry(res.config)
    ElMessage.error(r.message)
    return Promise.reject(new BizError(r.code, r.message, r.traceId))
  },
  (err) => {
    if (err.response?.status === 429) ElMessage.warning('操作太频繁，请稍后再试')
    return Promise.reject(err)
  }
)
```

```ts
// src/api/order.ts
export const createOrder = (data: CreateOrderDTO) =>
  service.post<CreateOrderResult>('/order/create', data, {
    headers: { 'Idempotency-Key': uuid() }
  })
```

> 拦截器需要单独处理两个"治理类"错误码（详见 04 文档 §15）：
> - `10002`：token 失效 → 先尝试 refresh，失败则清空登录态跳登录；
> - `20003`：账号被封禁 → **不重试、不刷新**，直接用 `r.data.banUntil` 弹封禁窗并清 token 跳登录；
> - `30009`：上架权限受限 → 用 `r.data.publishBanUntil` 弹"无法上架商品"窗，停留在当前页（不跳转）。

### 13.3 常见错误速查

| 现象 | 原因 |
|---|---|
| 所有接口 401 | 未带 token 或 token 过期；检查白名单路径拼写 |
| 游客点商品能进详情？ | 后端 P2 应返回 10002；若没拦，检查网关白名单是否把 `/product/**` 整体放开了（只允许 `/product/page` 与 `/category/tree`） |
| 游客看到超过 20 条 | P1 未做 `pageNum=1,pageSize=20` 强制，或前端忽略了 `guestLimited` 继续请求第 2 页 |
| 登录 20003 | 账号被封禁；`data.banUntil` 是解封时间，弹窗文案见 §1.10 |
| 被封禁但还能继续操作 | `token_version` 没自增，或网关没查 `mall:user:banned:{id}` / `mall:user:tv:{id}` |
| 解封后仍 401 | 正常现象：解封会 `token_version+1`，要求重新登录 |
| 发布 30009 | 上架权限被限制；`data.publishBanUntil` 是解禁时间（`can_publish=0`） |
| 注册 20006 | 邮箱已被注册（`uk_email`）；前端应把错误定位到 email 输入框 |
| 设置角色 10003 / 20008 | 只有 SUPER_ADMIN 能设角色；传 `SUPER_ADMIN` 或目标是超管都会被拒 |
| 404 且响应体是网关的 | 网关无该路由（检查前缀） |
| 500 且日志无 traceId | 网关 TraceIdFilter 顺序错 |
| 下单 10006 | 复用了旧的 `Idempotency-Key` |
| 下单 40004 | 选了"仅自提"但收货地址跨城（同城才允许自提） |
| 下单/支付 50002 | 订单不是 `UNPAID`（已支付或已取消） |
| 支付后仍显示待付款 | MQ `mall-order-paid` 未消费成功；查 payment 是否调了 `/inner/order/{orderNo}/notify-paid` |
| 强制下架后首页仍显示 | 商品缓存（`product:detail:{id}`）未失效，或列表走的是 Redis ZSet 旧快照 |
| 发布后首页没有 | 状态是 `DRAFT`（点了 Split Button 左侧才算发布）；或分类被停用 |

## 14 接口变更策略

1. **只增不改**：新增字段不影响旧前端；删除/改语义必须升版本（`/v2/...` 或新路径）。
2. 枚举新增值：前端 `enums.ts` 兜底显示原值，不因未知枚举崩溃。
3. 文档与代码同步：Knife4j 注解是唯一事实来源，本文档随接口评审更新。
4. 破坏性变更需在本文档 §15 记录并通知前端。
