## 0.1 此时 Codex 接手（2026-10-28 → 2026-10-29，v1.6.2 → v1.7.2）

> **此时 codex 接手。**

### 0.1.1 触发

用户反馈：后端 4399~4405 正在启动，但打开 `http://127.0.0.1:5173/` 没有反应。接手时的实际状态是：

- 7 个后端服务健康检查全部 `UP`；
- 5173 没有监听进程，Vite 实际未运行；
- `scripts/status.cmd` 同时把所有端口误报为“空闲”，与 `netstat` 和健康检查结果矛盾。

### 0.1.2 根因

1. Vite 进程已退出或没有成功拉起，所以浏览器连接 5173 被拒绝。
2. `scripts/_common.ps1` 依赖 `Get-NetTCPConnection` 判断端口；在受限终端/非管理员环境下该命令会报“拒绝访问”，而错误被 `SilentlyContinue` 吞掉，最终把已监听端口判成空闲。

### 0.1.3 修法

- `scripts/_common.ps1` 增加 `netstat -ano` 兜底来查监听 PID，`status`、端口清理、启动前检查统一使用该逻辑。
- `Start-Frontend` 改为幂等：5173 已健康就直接复用；端口被无响应进程占用时才清理并重启。
- 新增只启动前端的 `scripts/start-frontend.ps1` 与 `scripts/start-frontend.cmd`，不触碰正在运行的后端。
- 重新拉起 Vite，并验证首页、`/src/main.ts`、`/src/App.vue` 均可访问。

### 0.1.4 验证

## 1 第 11 轮：端口占用治理（v1.6 → v1.6.1）

### 1.1 触发

用户反馈：「每次修完代码后端口都会被占用，需要手动清进程才能重跑」。

### 1.2 根因

| 现象 | 成因 |
| --- | --- |
| 改完代码 IDEA 点 Run 报 `Port 4399 was already in use` | 我验证时用 `java -jar` 起的实例还在后台跑；这类进程由 pwsh 派生，脚本退出后不随之结束 |
| 手动 `Stop-Process` 后端口仍被占 | 只杀了父进程，`taskkill` 缺失时 JVM 子进程（4~8MB 空壳）继续持有监听句柄 |
| 构建报 `Unable to rename ... .jar to .jar.original` | 目标 jar 正被运行中的进程占用 |

### 1.3 修法

- `scripts/_common.ps1` 重写清理链路：`Get-PortOwner`（按端口反查进程）、`Kill-Tree`（`taskkill /PID x /T /F` 连子进程）、`Clear-Port`（最多重试 5 次并回报失败原因）、`Stop-ProjectServices`（命令行匹配 `mall-*/target` + 端口兜底 + 等待端口真正释放）。
- `Start-ProjectServices` 启动前先逐端口 `Clear-Port`，真正做到"随便起都行"。
- 新增 `scripts/free-ports.ps1` + `free-ports.cmd`：只清 4399~4405（及可选 5173），适合"在 IDEA 里点 Run 之前"用。
- `scripts/status.ps1` 增强：显示每个端口是**空闲还是被谁占用**（进程名 + pid），排查不用再开资源监视器。
- 只清本项目端口，Nacos(8848/8090)、Sentinel(8858)、Seata(8091)、MySQL(3306)、Redis(6379) 不受影响。

### 1.4 验证

在 7 个服务 + Vite 全部运行的状态下执行 `scripts/free-ports.cmd`：8 个端口逐一识别占用者 → 杀进程树 → `4401 已释放`…→ 结尾「全部端口已空闲，可以直接在 IDEA 里 Run」；`scripts/status.ps1` 复测 8 行全部 `空闲`。

### 1.5 使用约定

- 改完代码要自己起服务：直接 `scripts\restart-all.cmd`（停 → 构建 → 起，不会再撞 jar 占用）。
- 想用 IDEA 跑：先 `scripts\free-ports.cmd`，再点 Run。
- 想让后台跑起来：`scripts\start-all.cmd`。
## 2 第 10 轮：修「发布/存草稿」两个真缺陷（v1.5 → v1.6）

### 2.1 触发

用户："现在发布之间就消失掉，存草稿依旧服务器内部错误"。

### 2.2 根因（三个都在「编辑页」这条链上）

1. **编辑页点「发布」根本没让商品上线**：按 03 §P5 的约定 `PUT /product/{id}` 只改内容、不改状态，但前端编辑页把「发布」做成了只调 P5 —— 草稿（`DRAFT`）或已下架（`OFF_SHELF`）的商品改完仍是原状态，列表里看不到，用户感受就是**"发布完商品直接消失"**。真正该走的 `P9 草稿发布` / `P8 重新上架` 前端没调。
2. **编辑页「存草稿」被全量校验拦下**：`update()` 里 `draft` 只看库里现状，前端传的 `status=DRAFT` 不参与判断，于是走 `validate(dto,false)` 连价格、图片一起校验 → 10001「价格必须大于 0」/「至少上传 1 张商品图」。而 P5 的契约本是「可只传要改的字段」。
3. **`applyFields()` 无条件 set**：前端没传的字段（价格/分类/省市区）被写成 `null`，而 `t_product` 这几列是 `NOT NULL` 且无默认值 → SQL 报错 → 10007「服务繁忙，请稍后再试」（这个 10007 才是"服务器内部错误"那条提示的真实来源）。

### 2.3 修法

后端（`mall-product`）：

- `update()` 明确"**只改内容、不改状态**"，`LOCKED`（交易中）直接 10005 拒绝编辑；
- 校验按状态分流：`DRAFT` → `validate(dto,true)`（只校验标题，其余后补，P9 兜底）；在售 → 新增 `validatePartial(dto)` **只校验前端真传了的字段**，并做分类启用 + `checkPublishPermission`（受限时 30009）；
- `applyFields()` 改成"只有非 null 才覆盖"，未传字段保留旧值，不再撞 NOT NULL；
- 新增 `ProductMapper.markOnSale(id)`：`P7 重新上架` 和 `P9 草稿发布` 里用它把 `off_shelf_reason` 清空（`updateById` 会忽略 null 字段，清不掉）。

前端（`PublishView.vue`）：

- 编辑页点「保存并发布」时，先 `P5` 保存内容，再按原始状态补一步：`DRAFT` → `P9 /product/{id}/publish`，`OFF_SHELF` → `P8 /product/{id}/on-shelf`，这样才真的上线；
- 编辑页隐藏「存草稿」按钮（`SplitButton` 的 `show-draft="!isEdit"`），避免"在编辑页存草稿"这种语义含糊的操作；
- `http.ts` 的错误提示补两个分支：后端有业务体 → 显示 `message`；没有业务体（网关 502/504、反代错误页）→ 显示 `接口异常 <状态码> <METHOD> <url>`；超时 → `请求超时 <METHOD> <url>`。

### 2.4 验证

- `.tmp/probe7.js` 走网关跑三条链路，全部 `code=0`：①草稿 `P5`+`P9` → 详情 `ON_SALE`；②已上架 `P6 下架`+`P5`+`P8 上架` → 详情 `ON_SALE` 且价格已更新；③只传 `title` 的局部 `P5` → 成功（不再要求重传图片）。
- `node e2e/e2e-rest.js` → **67/67**。脚本顺手补了两处清理：开跑前若 bob 地址 ≥9 条先清空、跑完删除本次创建的地址，避免撞 20010「最多 10 条」。
- 7 个服务全部改用 `target/*.jar` 运行（此前是 IDEA 直接跑的，代码改动不会生效）；`mall-auth` 启动参数带 `--mall.captcha.enabled=false`，方便 E2E 登录。

### 2.5 遗留

- 浏览器里如果还报错，多数是旧 bundle：Ctrl+Shift+R 强刷。现在提示语会带「接口异常 状态码 方法 地址」，把这一行发我即可精确定位。

### 13.1 Nacos 控制台端口改 8090

> **状态：已执行 ✅**（`nacos.console.port=8090` 已生效，控制台 HTTP 200）

- **文件**：`D:\nacos\conf\application.properties`
- **改什么**：`nacos.console.port=8080` → `nacos.console.port=8090`
- **这是哪个功能的**：**不是业务功能，是"端口不打架"**。Nacos 3.x 把控制台（那个浏览器界面）默认放在 8080，而当时网关 `mall-gateway` 也规划在 8080。不改的后果：**网关启动直接端口占用失败**，或者你先起网关再起 Nacos 时 Nacos 起不来。
- **改完**：重启 Nacos，浏览器访问 `http://localhost:8090/nacos`（控制台认证默认开启，首次会让你设密码）。
- 一行命令（管理员 PowerShell）：
  ```powershell
  (Get-Content 'D:\nacos\conf\application.properties') -replace '^nacos\.console\.port=8080','nacos.console.port=8090' | Set-Content 'D:\nacos\conf\application.properties' -Encoding utf8
  ```
- **不改会怎样**：`8080` 只能有一个主人（当时网关也规划在 8080）。你现在不跑网关就没事，一旦开始写代码，第一天就会撞上；第 8 轮后网关挪到 **4399**，与 8090 彻底错开。

### 13.2 Seata 改成注册到 Nacos + 用 db 存储

- **文件**：`D:\seata-server-2.5.0（UI）\apache-seata-2.5.0-incubating-bin\seata-server\conf\application.yml`
- **原来是什么**：出厂配置 `registry.type: seata`（指向它自己的 namingserver `127.0.0.1:7091`）、`store.mode: file`（事务日志写本地文件）。
- **改成什么**：`registry.type: nacos`（注册到 Nacos，`application: seata-server`、`group: SEATA_GROUP`、`namespace: public`）+ `store.mode: db`（会话/分支事务落 MySQL 的 `mall_seata` 库）。
- **这是哪个功能的**：**分布式事务**。具体就是「下单」那一步——`mall-product` 扣库存（把商品置 `LOCKED`）和 `mall-order` 建订单在两个库，必须一起成功或一起回滚，否则会出现"库存锁了但没有单"或者"有单但库存没锁"。
  - 改 `registry.type: seata` → `nacos`：让客户端（`mall-product`/`mall-order`）**在 Nacos 里就发现 Seata**，不用你再单独启动 Seata 自带的 7091 命名服务。你现在不用它，但代码一写就要靠这个发现机制。
  - 改 `store.mode: file` → `db`：事务日志从本地文件改存 MySQL。`file` 模式只适合单机演示、重启会丢未完成事务；`db` 模式重启后能继续恢复，也是文档里写的方案。
- **不改会怎样**：客户端按 Nacos 找 Seata 会找不到（因为 Seata 没注册进去），下单时 `@GlobalTransactional` 直接抛"no available server"——**下单接口 100% 失败**，而且是运行时才发现，不是启动报错。
- 顺带：Seata 用 `mall_app` / `Mall@2026` 连 `mall_seata`，这个账号在 02 §3 的建库脚本里有。

> **状态：已执行 ✅**（注册 Nacos 成功、db 存储生效）
>
> **实际启动时踩到的两个坑（写代码前记住，换机器也要照做）**：
>
> 1. **Seata 发行包的 `lib\jdbc\` 目录里只有 `NOTICE.md`，没有 MySQL 驱动** → 启动直接抛
>    `StoreException: The driver {com.mysql.cj.jdbc.Driver} cannot be found in the path ...\lib\jdbc`。
>    解决：把 `mysql-connector-j-8.4.0.jar`（约 2.4MB）放进 `...\seata-server\lib\jdbc\`。已经放好了。
> 2. **`seata-server.bat` 里的 `java` 取自 PATH，而本机 PATH 上没有 java；且脚本带了 JDK 9 起已废弃的 `-Xloggc`**。
>    解决：直接用 JDK 21 的 java 启动（下面是实际用的命令，工作目录必须是 seata-server 根）：
>
>    ```powershell
>    $base = 'D:\seata-server-2.5.0（UI）\apache-seata-2.5.0-incubating-bin\seata-server'
>    $java = "$env:JAVA_HOME\bin\java.exe"   # D:\Jetbrains APP\JDK\bin\java.exe
>    Start-Process $java -WorkingDirectory $base -WindowStyle Hidden -ArgumentList @(
>      "-Dloader.path=$base\lib", '-Xmx2048m', '-Xms512m', '-Xss512k',
>      '-XX:MetaspaceSize=128m', '-XX:MaxMetaspaceSize=256m',
>      '-classpath', "$base\conf;$base\lib\*",
>      '-Dapp.name=seata-server',
>      "-Dbasedir=$base",
>      "-Dspring.config.location=$base/conf/application.yml",
>      "-Dspring.config.additional-location=$base/conf/",
>      "-Dlogging.config=$base/conf/logback-spring.xml",
>      '-jar', "$base\target\seata-server.jar"
>    )
>    ```
>
>    想用原来的 bat 也行，但要先 `$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"`，再把 bat 里的 `-Xloggc:... -verbose:gc` 删掉。

### 13.3 导入 `mall_seata` 的建表脚本

> **状态：已执行 ✅**（实际建出 5 张表：`global_table`、`branch_table`、`lock_table`、`distributed_lock`，另加 `vgroup_table`——2.5.0 的脚本比 1.x 多一张分组表）

- **脚本**：`D:\seata-server-2.5.0（UI）\apache-seata-2.5.0-incubating-bin\seata-server\script\server\db\mysql.sql`
- **做什么**：在 `mall_seata` 库里执行，建三张表——`global_table`（全局事务）、`branch_table`（分支事务）、`lock_table`（行锁）。
- **这是哪个功能的**：**Seata AT 模式的存储底座**。就是 7.2 里 `store.mode: db` 要写的那三张表。没有它们，Seata 启动后第一笔全局事务就会报 `Table 'mall_seata.global_table' doesn't exist`。
- **不改会怎样**：下单时 Seata 服务端报错、全局事务开不起来，和 7.2 一样是**下单失败**。
- 注意：`undo_log` **不在这个库里**——它在业务库（`mall_product`、`mall_order`），由 02 §9.1 的 DDL 建，跟着业务库一起建。

### 13.4 三件事的关系

```
下单（Seata AT 全局事务）
 ├─ 需要 Seata 服务端「已注册到 Nacos」       ← 7.2 的 registry 改 nacos
 │    └─ 需要 Nacos 控制台「不占用 8080」      ← 7.1（否则 Nacos 起不来，Seata 注册不上）
 ├─ 需要 Seata 能「持久化事务状态」            ← 7.2 的 store.mode=db
 │    └─ 需要 mall_seata 库「有三张表」        ← 7.3
 └─ 需要业务库有 undo_log                      ← 02 §9.1（建库时一起建）
```

一句话：**7.1 是 7.2 的前提，7.2 是 7.3 的前提，三件合起来才是"下单能成功"。**
